# 06 美誉值进阶专题

> 简介段：本篇是 MeriToken 主题集合的扩展位，承接 [01-meritoken-overview.md](./01-meritoken-overview.md) 至 [05-meritoken-credential.md](./05-meritoken-credential.md) 的全部前置约定，把美誉值（MeriToken）在新社会中的两类高密度使用情境——「跨主体协作中的高密度使用」与「滚动场景」——作为独立专题展开。每个专题不重复主线已经讲过的概念，而是把主线机制放进具体压力场景下再观察一次。

## 背景

主线的 01–05 篇已经把美誉值的位置、技术原理、社会内涵、引用与应用、与 `credential` 的边界讲清楚。但在新社会真正落地后，会出现两类「高负载」情境，主线既有论述并不能直接覆盖：

- **跨主体高密度使用**：当多个 `Fay` 主体与多个个人主体在同一议题下持续引用美誉值时，单条引用看似简单，叠加起来却会带来开销、披露、聚合三类难题。
- **滚动场景**：当协作的生命周期足够长，美誉值不再是一次性产出物的留痕，而是要经过多轮累积、修订、撤回、归档的循环。这要求美誉值机制在长时间尺度上保持自洽，而不是只在单次引用上看上去合理。

本篇按这两类专题展开。每个专题先简述压力来源，再把主线机制（取用、披露、留痕、所有权与使用权、`credential` 边界等）放进该压力下重新审视，并指出值得后续论证或工程化的开放点。本篇不引入新的协议层概念，所有内容都是主线已定义机制在新场景下的继续推演。

## 核心内容

### 专题 A：跨主体协作中的高密度使用

**压力来源**：在新社会的真实协作中，「一个 `Fay` 主体引用一条美誉值」是一种过于理想的最小情境。实际更常见的是：在同一议题下，三类引用源同时出现——

- **多个 `Fay` 主体**：例如不同行业、不同地域的协作方各自代表自己的成员引用相关美誉值；
- **多个个人主体**：例如该议题的关键参与者各自援引自己历次相关协作的美誉值条目；
- **嵌套引用**：上述 `Fay` 主体本身又引用了若干个人主体的美誉值条目作为其代表权依据。

这种高密度引用在同一议题、同一时段、同一披露面之内同时发生，会把美誉值机制的几条性质同时拉到压力极限。

**机制再审视**：

- **引用聚合的边界**：每个 `Fay` 主体的聚合式引用本身已经是一个复合引用面（参见 [04-meritoken-usage.md](./04-meritoken-usage.md) 的「`Fay` 主体的引用方式与应用场景」段）。当多个 `Fay` 主体的复合引用面在同一议题下叠加，外部审视方需要的不是「每条美誉值都展开」，而是「能否在不展开明细的前提下确认这些聚合面互不矛盾」。这意味着聚合式引用必须支持「聚合层面的可对账性」，而不仅是单条层面的可验证性。
- **披露分级的协调**：高密度使用下，每位被引用方（个人主体或下层 `Fay` 主体）的披露许可档位可能各不相同。聚合方不能把高披露档与低披露档混在一起对外呈现，否则会等价于把低披露档强行升档。专题 A 要求「最低披露档兜底」原则——聚合面对外的披露档位不高于其中任一被引用条目的最低许可档，仅在所有被引用方主动同意时才整体升档。
- **撤回路径的回波**：当某个底层个人主体撤回其披露许可时，依赖该条目的所有 `Fay` 主体聚合面都应同时失效相应分量；不允许出现「上游撤回但下游聚合仍以缓存形式持续暴露」的情况。这把 [02-meritoken-technical.md](./02-meritoken-technical.md) 「隐私保证」段的「撤回与失效」语义推广到嵌套场景。
- **取用留痕的可读性**：在高密度场景下，每次引用都按 `GMC` 留痕会让单议题的留痕量迅速膨胀。机制层面留痕仍然必要，但向人类呈现时需要按「议题—主体—时间」三轴折叠，避免把审计过程淹没在原始留痕条目里。

**开放点**：

- 聚合层面的可对账性具体由哪一组承诺机制承担，需要与 `GMC` 上位规则一起设计；
- 「最低披露档兜底」与个别参与方希望整体升档之间的协商流程，应当本身以美誉值条目形式记录；
- 留痕折叠的呈现规则不是协议层问题，但需要由蓝图配套的工具链统一约定。

### 专题 B：滚动场景

**压力来源**：长生命周期项目中，美誉值不会停留在「一次贡献—一次评价—一次留痕」的最小单元，而会在长时间尺度上累积、修订、撤回、归档循环出现。典型情境包括跨代际的公共项目、长期演进的开源协作、面向多届参与者的社群治理。这类项目带来的压力不再是单次引用的复杂度，而是机制在长时间尺度上的自洽性。

**机制再审视**：

- **累积**：项目的每一阶段都会沉淀新的美誉值条目，这些条目按 `GMC` 留痕，不会因为阶段切换而丢失。但项目对外的「整体面貌」需要避免把所有条目无差别堆叠——按阶段、按角色、按议题分层组织是必要的。这与 [03-meritoken-social.md](./03-meritoken-social.md) 「个人成长映射」段中「从单点能力到多维画像」的思路一致，但在项目侧需要由 `Fay` 主体承担分层归集职责。
- **修订**：原有美誉值条目在事实层出现新见证、新评价、新对照时，应通过追加修订条目而非覆写原条目。修订条目本身也是美誉值条目，包含修订理由与多方共签。读者按时间线既能看到原始条目，也能看到后续修订，避免「单条目反复改写抹平历史」。
- **撤回**：长生命周期下，撤回不仅指披露许可的撤回，也包括对原始条目效力的撤回（例如签发方退出、协作前提变更）。效力撤回不删除留痕，但会在条目状态层标注为「已撤回」，后续引用方应当能够区分「在撤回前的引用」与「在撤回后的引用」。撤回操作本身遵循 [05-meritoken-credential.md](./05-meritoken-credential.md) 「边界与对位关系」段定义的独立撤回路径，不与 `credential` 的回收路径互相代偿。
- **归档**：项目阶段性结束或整体结束时，相关美誉值条目应进入归档状态而非被销毁。归档状态下条目仍可被独立验证、被援引；但默认披露档位降到最低，避免长期项目结束多年后仍以高披露档继续暴露参与者。归档转换本身记录在 `GMC` 上，避免出现「某个时点之后条目悄悄改变可见性」的不透明现象。

**机制自洽性**：累积 / 修订 / 撤回 / 归档构成一组完整循环，每一动作都以新条目形态留痕。这保证了「时间」这一维度本身被纳入美誉值机制，而不是从外部由项目方单方面控制。任何在时间维度上的状态变化都应当能被独立验证，不依赖项目方的解释。

**开放点**：

- 修订条目的多方共签范围是否需要严格等同于原条目，需要按场景细化；
- 归档转换的默认披露档位是否可由项目方与参与者集体调整，需要给出协商流程；
- 跨阶段引用的权重是否随时间衰减，是个体项目的策略选择，应当被工具链支持而非被协议层强制。
