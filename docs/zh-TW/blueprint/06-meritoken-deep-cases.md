# 06 美譽值進階專題

> 簡介段：本篇是 MeriToken 主題集合的擴展位，承接 [01-meritoken-overview.md](./01-meritoken-overview.md) 至 [05-meritoken-credential.md](./05-meritoken-credential.md) 的全部前置約定，把美譽值（MeriToken）在新社會中的兩類高密度使用情境——「跨主體協作中的高密度使用」與「滾動場景」——作為獨立專題展開。每個專題不重複主線已經講過的概念，而是把主線機制放進具體壓力場景下再觀察一次。

## 背景

主線的 01–05 篇已經把美譽值的位置、技術原理、社會內涵、引用與應用、與 `credential` 的邊界講清楚。但在新社會真正落地後，會出現兩類「高負載」情境，主線既有論述並不能直接覆蓋：

- **跨主體高密度使用**：當多個 `Fay` 主體與多個個人主體在同一議題下持續引用美譽值時，單條引用看似簡單，疊加起來卻會帶來開銷、披露、聚合三類難題。
- **滾動場景**：當協作的生命週期足夠長，美譽值不再是一次性產出物的留痕，而是要經過多輪累積、修訂、撤回、歸檔的循環。這要求美譽值機制在長時間尺度上保持自洽，而不是只在單次引用上看上去合理。

本篇按這兩類專題展開。每個專題先簡述壓力來源，再把主線機制（取用、披露、留痕、所有權與使用權、`credential` 邊界等）放進該壓力下重新審視，並指出值得後續論證或工程化的開放點。本篇不引入新的協議層概念，所有內容都是主線已定義機制在新場景下的繼續推演。

## 核心內容

### 專題 A：跨主體協作中的高密度使用

**壓力來源**：在新社會的真實協作中，「一個 `Fay` 主體引用一條美譽值」是一種過於理想的最小情境。實際更常見的是：在同一議題下，三類引用源同時出現——

- **多個 `Fay` 主體**：例如不同行業、不同地域的協作方各自代表自己的成員引用相關美譽值；
- **多個個人主體**：例如該議題的關鍵參與者各自援引自己歷次相關協作的美譽值條目；
- **嵌套引用**：上述 `Fay` 主體本身又引用了若干個人主體的美譽值條目作為其代表權依據。

這種高密度引用在同一議題、同一時段、同一披露面之內同時發生，會把美譽值機制的幾條性質同時推到壓力極限。

**機制再審視**：

- **引用聚合的邊界**：每個 `Fay` 主體的聚合式引用本身已經是一個複合引用面（參見 [04-meritoken-usage.md](./04-meritoken-usage.md) 的「`Fay` 主體的引用方式與應用場景」段）。當多個 `Fay` 主體的複合引用面在同一議題下疊加，外部審視方需要的不是「每條美譽值都展開」，而是「能否在不展開明細的前提下確認這些聚合面互不矛盾」。這意味著聚合式引用必須支援「聚合層面的可對帳性」，而不僅是單條層面的可驗證性。
- **披露分級的協調**：高密度使用下，每位被引用方（個人主體或下層 `Fay` 主體）的披露許可檔位可能各不相同。聚合方不能把高披露檔與低披露檔混在一起對外呈現，否則會等價於把低披露檔強行升檔。專題 A 要求「最低披露檔保底」原則——聚合面對外的披露檔位不高於其中任一被引用條目的最低許可檔，僅在所有被引用方主動同意時才整體升檔。
- **撤回路徑的回波**：當某個底層個人主體撤回其披露許可時，依賴該條目的所有 `Fay` 主體聚合面都應同時失效相應分量；不允許出現「上游撤回但下游聚合仍以快取形式持續暴露」的情況。這把 [02-meritoken-technical.md](./02-meritoken-technical.md) 「隱私保證」段的「撤回與失效」語義推廣到嵌套場景。
- **取用留痕的可讀性**：在高密度場景下，每次引用都按 `GMC` 留痕會讓單議題的留痕量迅速膨脹。機制層面留痕仍然必要，但向人類呈現時需要按「議題—主體—時間」三軸折疊，避免把審計過程淹沒在原始留痕條目裡。

**開放點**：

- 聚合層面的可對帳性具體由哪一組承諾機制承擔，需要與 `GMC` 上位規則一起設計；
- 「最低披露檔保底」與個別參與方希望整體升檔之間的協商流程，應當本身以美譽值條目形式記錄；
- 留痕折疊的呈現規則不是協議層問題，但需要由藍圖配套的工具鏈統一約定。

### 專題 B：滾動場景

**壓力來源**：長生命週期專案中，美譽值不會停留在「一次貢獻—一次評價—一次留痕」的最小單元，而會在長時間尺度上累積、修訂、撤回、歸檔循環出現。典型情境包括跨代際的公共專案、長期演進的開源協作、面向多屆參與者的社群治理。這類專案帶來的壓力不再是單次引用的複雜度，而是機制在長時間尺度上的自洽性。

**機制再審視**：

- **累積**：專案的每一階段都會沉澱新的美譽值條目，這些條目按 `GMC` 留痕，不會因為階段切換而遺失。但專案對外的「整體面貌」需要避免把所有條目無差別堆疊——按階段、按角色、按議題分層組織是必要的。這與 [03-meritoken-social.md](./03-meritoken-social.md) 「個人成長映射」段中「從單點能力到多維畫像」的思路一致，但在專案側需要由 `Fay` 主體承擔分層歸集職責。
- **修訂**：原有美譽值條目在事實層出現新見證、新評價、新對照時，應透過追加修訂條目而非覆寫原條目。修訂條目本身也是美譽值條目，包含修訂理由與多方共簽。讀者按時間線既能看到原始條目，也能看到後續修訂，避免「單條目反覆改寫抹平歷史」。
- **撤回**：長生命週期下，撤回不僅指披露許可的撤回，也包括對原始條目效力的撤回（例如簽發方退出、協作前提變更）。效力撤回不刪除留痕，但會在條目狀態層標註為「已撤回」，後續引用方應當能夠區分「在撤回前的引用」與「在撤回後的引用」。撤回操作本身遵循 [05-meritoken-credential.md](./05-meritoken-credential.md) 「邊界與對位關係」段定義的獨立撤回路徑，不與 `credential` 的回收路徑互相代償。
- **歸檔**：專案階段性結束或整體結束時，相關美譽值條目應進入歸檔狀態而非被銷毀。歸檔狀態下條目仍可被獨立驗證、被援引；但預設披露檔位降到最低，避免長期專案結束多年後仍以高披露檔繼續暴露參與者。歸檔轉換本身記錄在 `GMC` 上，避免出現「某個時點之後條目悄悄改變可見性」的不透明現象。

**機制自洽性**：累積 / 修訂 / 撤回 / 歸檔構成一組完整循環，每一動作都以新條目形態留痕。這保證了「時間」這一維度本身被納入美譽值機制，而不是從外部由專案方單方面控制。任何在時間維度上的狀態變化都應當能被獨立驗證，不依賴專案方的解釋。

**開放點**：

- 修訂條目的多方共簽範圍是否需要嚴格等同於原條目，需要按場景細化；
- 歸檔轉換的預設披露檔位是否可由專案方與參與者集體調整，需要給出協商流程；
- 跨階段引用的權重是否隨時間衰減，是個體專案的策略選擇，應當被工具鏈支援而非被協議層強制。
