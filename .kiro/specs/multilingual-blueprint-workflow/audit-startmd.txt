# Task 1.5 — `git check-ignore` 白名单 / 黑名单样本验证

## 工具元数据

- 命令：`git check-ignore -v <path>` 与 `git check-ignore <path>`
- 工作目录：仓库根
- Git 版本：`git version 2.50.1 (Apple Git-155)`

## 退出码语义说明（重要）

Git 官方手册中 `git check-ignore` 的退出码定义：

- **退出码 0**：至少一个路径被「忽略」。
- **退出码 1**：没有路径被忽略。
- **退出码 128**：致命错误。

但加上 `-v` 之后行为有一处微妙差异：当一个路径是被 `!` 反向放行规则匹配（例如本仓库 `.gitignore` 中的 `!docs/**`、`!.kiro/**`），`-v` 会把这条**反向规则也算作「匹配到的规则」打印出来，并以退出码 0 退出**——尽管该路径在语义上**没有被忽略**。Git 文档对此的描述：

> ... -v ... With this option, every value provided ... will be treated as if it has been matched against a particular rule, even if that rule is a "negative" rule (an unignore pattern).

因此在白名单样本上，以下两种合法行为都对应「未被忽略」的同一语义：

- 退出码 1（无输出）：路径不被任何规则匹配，例如 `README.md`、`LICENSE` 这两份在仓库根、被显式追踪、且不属于 `docs/` / `.kiro/` 子树的文件。
- 退出码 0 + 行首打印 `!docs/**` 或 `!.kiro/**` 一类的反向规则：路径被反向放行规则匹配。

为给出无歧义的「是否忽略」结论，本节同时给出 `git check-ignore <path>`（不带 `-v`）的退出码——它的退出码语义与「是否忽略」严格 1:1：

- `git check-ignore <p>` 退出码 1 ⇔ p **未被忽略**（白名单期望）
- `git check-ignore <p>` 退出码 0 ⇔ p **已被忽略**（黑名单期望）

下表把两种调用都记录下来，便于核对。

## 白名单样本（期望：未被忽略）

| # | 路径 | `git check-ignore -v` 输出 | `-v` 退出码 | `git check-ignore` 退出码 | 是否被忽略 | 与期望一致 |
|---|------|----------------------------|-------------|---------------------------|-----------|-----------|
| 1 | `docs/zh-CN/blueprint/00-overview.md` | `.gitignore:13:!docs/**  docs/zh-CN/blueprint/00-overview.md` | 0（反向规则匹配） | 1 | 否 | ✅ |
| 2 | `README.md` | （无输出） | 1 | 1 | 否 | ✅ |
| 3 | `.kiro/specs/multilingual-blueprint-workflow/design.md` | `.gitignore:10:!.kiro/** .kiro/specs/multilingual-blueprint-workflow/design.md` | 0（反向规则匹配） | 1 | 否 | ✅ |
| 4 | `LICENSE` | （无输出） | 1 | 1 | 否 | ✅ |

注：

- 样本 2 / 4 的 `-v` 输出为空且退出码为 1，是因为 `README.md` 与 `LICENSE` 不在 `docs/` 或 `.kiro/` 子树下，不会触达 `!docs/**` / `!.kiro/**` 反向规则；它们已在 Task 1.4 提交进入索引（`git ls-files` 命中），属于「已追踪、且无任何 ignore 规则匹配」的状态，对应 `git check-ignore` 的退出码 1。
- 样本 1 / 3 的 `-v` 之所以退出码 0 而非 1，仅是 `-v` 模式把反向规则也回显的副作用，**并不代表它们被忽略**；不带 `-v` 的退出码 1 才是无歧义结论。

## 黑名单样本（期望：被忽略）

| # | 路径 | `git check-ignore -v` 输出 | `-v` 退出码 | `git check-ignore` 退出码 | 是否被忽略 | 与期望一致 |
|---|------|----------------------------|-------------|---------------------------|-----------|-----------|
| 5 | `scratch.txt` | `.gitignore:3:*  scratch.txt` | 0 | 0 | 是 | ✅ |
| 6 | `build/output.json` | `.gitignore:3:*  build/output.json` | 0 | 0 | 是 | ✅ |
| 7 | `docs/en/blueprint/node_modules/foo.js` | `.gitignore:20:docs/**/node_modules/     docs/en/blueprint/node_modules/foo.js` | 0 | 0 | 是 | ✅ |
| 8 | `tmp/secret.env` | `.gitignore:3:*  tmp/secret.env` | 0 | 0 | 是 | ✅ |

注：

- 样本 5 / 6 / 8 命中 `.gitignore` 第 3 行的 `*` 兜底规则——它们位于仓库根或非白名单子树（`build/`、`tmp/`），因此「先全量忽略」的兜底规则生效。
- 样本 7 命中 `.gitignore` 第 20 行的 `docs/**/node_modules/` 显式黑名单，演示了「在已放行的 `docs/**` 子树内再次精准屏蔽常见杂项目录」的设计意图。

- 黑名单 4 / 4 全部「被忽略」，与设计「白名单外路径被兜底 `*` 或精准黑名单忽略」一致 → Requirements 2.4 通过。

## 用途
